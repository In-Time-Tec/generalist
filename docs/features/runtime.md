# Runtime

`@batonfx/runtime` admits addressed Messages into finite Runs, appends one canonical `RunEvent` stream per Run, and exposes `send`, `spawn`, `fanOut`, `awaitFanOut`, `steer`, `events`, `respond`, `signal`, `cancel`, `inspect`, `inspectFanOut`, `snapshot`, finite `history`, and finite `list`. A blocking ask is not a Runtime primitive.

- `Address` is an opaque routing key bound to a pinned `AgentRef` through Layers. `Message` wraps Effect AI `Prompt` with idempotency, session/lane, and correlation fields and does not introduce a second content vocabulary.
- Ordinary admission is FIFO per `(Address, Session)`. Only the lane head is runnable. `respond`, `signal`, and `cancel` target an existing Run and bypass the lane so waiting work cannot deadlock successors.
- Exact duplicate idempotency keys return the same `RunReceipt`. A changed payload for the same key fails typed. `send.runId` optionally constrains admission to a caller-assigned stable identity; an idempotency replay or existing Run bound to another identity fails as `RunIdConflict`. First terminal event wins among completed, failed, and cancelled.
- `steer` persists an idempotent FIFO inbox entry for one nonterminal Run. Equivalent duplicate keys succeed; changed prompts fail as `SteeringConflict`. AgentHost reads pending entries without removing them and consumes the exact batch atomically with the next model operation and DriverCheckpoint. Completion either commits terminal state or reports pending steering in the same store transaction, then AgentHost continues from the completed transcript.
- Each Run has one stream with stable `eventId` values and a strictly increasing per-Run sequence. Followers replay `sequence > cursor`, then follow live. Subscriber queues are bounded; lag and unavailable cursors fail typed without blocking the producer.
- `snapshot` atomically pairs `RunInspection` with its exclusive cursor. `history` and `list` require finite limits. Inspection exposes the schema-backed `RunWait`, including its structured `WaitResolution` after response or signal.
- `RunEvent` is a strict producer schema composed from lifecycle schemas, core model telemetry, and precise core event part schemas. Only payload fields that are intentionally dynamic, such as tool values and metadata, remain unknown.
- Wait resolution is durable. `Approved` continues the authorization path; `Denied`, `ToolResult`, and `Signal` are applied to the authoritative core suspension on re-entry rather than redispatching a resolved suspended call.
- Parent streams persist child link and terminal projection only. Child detail remains in the child stream. `RunTree.history` and `RunTree.events` project an arbitrary-depth tree in one dense root order with one opaque, root-bound cursor. Each projected event carries authoritative root, Run, parent, invocation, and explicitly derivable model/tool call identities; the projection index references canonical event rows and is not a second lifecycle log.
- `fanOut` admits one immutable ordered member set under a parent Run. The `(parentRunId, idempotencyKey)` pair returns one stable aggregate and deterministic child Run IDs; changed member order or policy fails as `FanOutConflict`. Transactional member state limits claimable children to `concurrency`, promotes pending members in ordinal order, and stores results by ordinal rather than completion order.
- Join rules are `AllSuccess`, `AllSettled`, `FirstSuccess`, `Quorum`, and `BestEffort`. Remainder rules are `await`, `request-cancel`, and `abandon`; `terminate` fails as `FanOutRemainderUnsupported` because no current host can prove external-effect termination. Child terminal state, member outcome, join decision, and next promotion commit in one store transaction. Parent cancellation cancels and settles every owned member before the parent terminal event.
- `run_operations` records model/tool/memory/compaction/send/structured-output work with requested/running/succeeded/failed/unknown. Expired non-idempotent running operations become `unknown` and never blind-retry. Pure or provider-idempotent operations may return to requested.
- `RunStore.layerMemory` / `Runtime.layerMemory` are ephemeral in-memory stores. They preserve admission, idempotency, FIFO, control-input, wait/signal, cancellation, child-link, operation, and replay contracts, but release loses all state.
- `RunStore.layerSqlite` / `Runtime.layerSqlite` are durable single-process SQLite stores. Capability reports `durability: "durable"`, `backend: "sqlite"`, `multiWorker: false`. Multi-worker configuration fails typed as `MultiWorkerUnsupported`.
- SQLite acquires with WAL, foreign keys, and `BEGIN IMMEDIATE` transactions. Schema migration runs automatically at Layer acquisition through Effect SQL migrations, then verifies dirty flag, checksum, and supported version. Dirty, checksum mismatch, unsupported forward version, and migration failure are typed schema errors.
- `Runtime.layerPostgres` is the durable multi-worker PostgreSQL store. Capability reports `durability: "durable"`, `backend: "postgres"`, `multiWorker: true`. Correctness reuses SQLite's relational state machine, including dedicated `baton_fan_outs` and `baton_fan_out_members` tables, plus `baton_schema_meta` / migrator metadata, with Postgres types (`BOOLEAN`, `TIMESTAMPTZ`) and claim columns (`owner_worker_id`, `lease_expires_at`, monotonic `attempt_fence`).
- PostgreSQL Runtime startup is verify-only: typed `SchemaUpgradeRequired`, `SchemaDirty`, `SchemaChecksumMismatch`, and `SchemaVersionUnsupported` failures. Predeploy jobs use `RunSchema.plan`, `RunSchema.check`, and `RunSchema.apply`. Runtime credentials must not need DDL. Schema version 3 adds fan-out aggregates and ordered members; migrations 1 and 2 remain immutable.
- Multi-worker ready-run claims use `FOR UPDATE SKIP LOCKED`, database-time leases, monotonic attempt epochs, lease refresh/recovery, stale-owner zero-row commits (`StaleClaim`), only-head-ready lane promotion, and concurrency-proportional claim plans via `RunClaims` / `RuntimeWorker`.
- Event append batches allocate per-Run sequences with `UPDATE … RETURNING` (no `MAX` races). PostgreSQL `LISTEN`/`NOTIFY` is only a coalesced pointer hint; replay-after-cursor and polling remain authoritative so followers on different Runtime instances observe identical history.
- Schema migration 4 creates one root counter and tree event index. Existing events are backfilled deterministically per root by Run identity and numeric Run sequence; historical cross-Run commit order was not recorded and is not inferred.
- `AgentHost` reconstructs the pinned core Agent and DriverCheckpoint, provides a fenced `DriverJournalService`, persists each operation before dispatch, maps Agent events into RunEvent, and commits suspension or terminal state. `RuntimeWorker.layerWorker` claims ready PostgreSQL Runs and executes them through this host.
- Opaque canonical JSON text is stored with schema codecs; correctness queries do not inspect JSON payloads.
- `Runtime.layerMysql` is the durable multi-worker MySQL 8+ store. It has the same relational state machine, verify-only startup, database-time leases, monotonic attempt fences, stale-owner rejection, bounded fan-out claims, and lane-head claims as PostgreSQL. `MysqlRunSchema.plan`, `check`, `apply`, and `markDirty` own predeploy schema work; `apply` serializes DDL with a named migration lock.
- MySQL transactions run at `READ COMMITTED`. Claims use bounded candidate scans plus primary-key `FOR UPDATE SKIP LOCKED`, and deadlocks retry the whole transaction. Writes do not rely on `RETURNING`; rows are read after fenced updates, booleans decode from `TINYINT(1)`, and timestamp strings decode at the store boundary.
- MySQL event delivery is polling-backed for local and cross-process followers. Each subscription owns its poller scope, registers before polling begins, and advances from committed durable history after the exclusive cursor.
