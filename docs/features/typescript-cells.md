# TypeScript cells

A cell is one model-authored TypeScript source executed in the persistent kernel that a TenetKit Session owns. `tenetkit/repl` owns the provider-neutral contract; `tenetkit/repl/bun` supplies the built-in trusted-local process implementation, and hosted implementations remain explicit host-provided Layers. A `CodeExecutor` is separate: it evaluates each Agent Program afresh and never owns a Session's ordered REPL namespace.

- An agent advertises exactly one cell tool, `typescript`, whose parameters are exactly one bounded string field named `code`. Because one namespace is shared, `CellTool.scheduling` is always `maxConcurrency: 1` with no parallel-safe tool, so every cell is an authored-order exclusive barrier.
- Success is `CellResult`: the complete formatted value, stdout and stderr, duration, and kernel epoch.
- Failure is the closed `CellFailure` union with `failureMode: "return"`, so a failed cell re-enters the model as an observation rather than failing the run. `CellExecutionFailed` means the cell threw and the namespace survived; `KernelUnavailable` means nothing was evaluated; `KernelProtocolViolation` means the kernel broke the cell protocol; `CellOutcomeUnknown` means the cell may or may not have committed and a host must resolve it explicitly.
- `CellEvent` is the closed union of `KernelStarting`, `KernelReady`, `Stdout`, `Stderr`, `HostCall`, `Result`, `Display`, `StateRestored`, `StateLost`, and `KernelRestarted`. Every event carries its `cellId` and a cell-local `sequence` that starts at 0 and increases by exactly one per emitted event; `Cell.validateSequence` rejects a gap, a repeat, a non-zero start, and interleaving from a second cell. The cell route emits one `ToolContext` progress update per event, so a host observes cell lifecycle through the existing tool-progress seam.
- `KernelProfile` identifies one kernel epoch by contract version, protocol version, immutable provider, exact runtime plus runtime/image/template identity, physical isolation (`host-process`, `container`, or `microvm`), explicit checkpoint capabilities, bindings digest, workspace paths, and source and execution limits. It declares no credential, mutable provider-resource ID, owner, or generation field. Unknown keys are dropped from both the encoded form and the digest, so a host cannot widen it by attaching extra data. Free-text identifiers and paths are host-supplied and are not scanned; a host must not put a secret there. A foreign protocol version fails to decode. `KernelProfile.digest` is the content-addressed identity, and a changed profile requires a replacement epoch rather than reuse.
- `KernelPool` exposes exactly `execute`, `inspect`, `interrupt`, `restart`, and `close`, all keyed by Session identity. It does not expose provider create, pause, resume, or billing primitives. `KernelSnapshotStore` remains the best-effort namespace snapshot port whose manifest names every binding restored by value, source, or import replay and every binding dropped with its reason. `HostBindings` mounts named Schema-typed modules into the kernel namespace; duplicate module or operation names are rejected, host failures are tagged as cell data, and schema faults are reported per stage.
- `KernelResourceAuthority` is the separate host-owned authority for external kernel resources, not Runtime Run fencing and not `KernelSnapshotStore`. It issues a monotonically increasing ownership generation per Session and atomically owns the exact Session/owner/generation/profile/resource/epoch binding, sole admitted cell, lease renewal, revoke-before-delete transition, and retained retryable deletion failure. Every remote command and response carries an exact command claim. A provider-side boundary must call `admit` immediately before acting; a host-side lease check followed by an unfenced provider call is not conformant. Mutable resource IDs and cleanup diagnostics remain host-only.
- Exactly one live or paused resource and one admitted cell may exist per Session; different Sessions may proceed concurrently. After lease expiry, a new host acquires a greater generation and either reconnects the same exact resource or replaces it honestly. Every operation from the stale host is rejected. Connection loss before admission proves that source did not run. Loss after admission without a matching terminal response is `CellOutcomeUnknown`, and that source is never replayed automatically.
- Recovery uses four non-interchangeable terms. `live-process` means the same paused process continued; `filesystem` means only a provider filesystem checkpoint continued; `namespace` means TenetKit best-effort binding restoration continued; `restart-only` means no prior state continued. `Inspection.recovery` and `Restart.recovery` report what actually happened, not what the profile says is possible. Idle pause is allowed only with no admitted cell. `close` deletes live and paused resources; failed deletion remains visible and retryable until the exact resource is proven gone.
- Kernel state is working memory, never durable authority. TenetKit operations, events, Session entries, and children remain the only truth; a restart reports exactly what was restored and what was lost; and an uncertain cell is never replayed.
- The Bun pool preserves its trusted-local child-process behavior and uses filesystem plus best-effort namespace recovery; it does not opt into hosted network or billing behavior. `TestKernel` supplies in-memory `KernelPool`, `KernelSnapshotStore`, and resource-authority implementations. `tenetkit/test` exports `KernelProviderConformance.kernelProviderConformance`, which runs the shared lifecycle guarantees against any provider and adds deterministic two-host, generation, reconnect, uncertain-outcome, pause, and cleanup guarantees for remote providers. That deterministic suite cannot prove a vendor's microVM isolation or billing cleanup; a real hosted adapter still needs live provider gates.
