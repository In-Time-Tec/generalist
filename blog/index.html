    Killing Relay: Building a Baton-Native Runtime

    A long-form decision record on why Relay became too big, what we learned, and how Baton becomes the only durable agent framework Rika builds on — with fewer concepts, one authority, and Effect-native semantics end to end.

    Branch feat/native-runtime · Baton 0.13.1 · Effect 4.0.0-beta.98

    Executive summary

    Relay started as the durable, addressable agent layer on top of Baton. It grew into a full platform: address books, envelopes, executions, workflows, fan-out hosts, session registries, cluster topology, and dozens of Postgres tables — plus a fat SDK and a fat Rika adapter on top.

    The fix is not Relay v2 in a new repo. The fix is to fold durability into Baton itself as @batonfx/runtime, keep the agent loop in @batonfx/core, delete Relay, and rebuild Rika on a thin TurnExecution seam — not another Relay-shaped adapter.

    North star: Baton is the AI agent framework in the Effect ecosystem — single agent, multi-agent, and addressable agent-to-agent — with memory, SQLite, Postgres, and MySQL backends. One event log. One Run authority. No second scheduler.

    Rika was always meant to be a product: threads, turns, TUI, workspace policy. Baton was always meant to be the agent framework: loop, tools, models, budgets. Relay sat in the middle and eventually owned durability, addressing, multi-agent orchestration, transport framing, and half the vocabulary Rika needed to translate anyway.

    Every bug, every performance investigation, every "why does restart do X?" question had to cross three layers. That is the core failure mode we are fixing.

    What went wrong with Relay

    Relay is not "bad code." It is too many independent concepts for what we actually need.

    Concept sprawl

    Relay currently owns all of this as separate domains:

    • Address book and route attempts
    • Envelopes (fire-and-forget messages)
    • Executions (durable runs)
    • Event log and cursors
    • Waits and approvals
    • Workflows and activities
    • Child executions and fan-out state
    • Tool calls, attempts, placement, results
    • Sessions and session entries
    • Context epochs, durable memory, permissions
    • Steering, compaction, skills, schedules
    • Workspaces and cluster topology

    Two recovery authorities

    Relay built on Effect Cluster and Workflow. Baton has its own agent loop with nondeterministic operations (model calls, tools, compaction). Cluster gives you shards and RPC mailboxes; Workflow gives you activities — but neither gives you:

    • Monotonic worker fencing the way Baton needs
    • Explicit unknown outcomes for non-idempotent external effects
    • Independent multi-client cursors on one Run stream
    • FIFO per (Address, Session) without control deadlock

    Using Cluster would mean two recovery journals: Cluster/Workflow state plus everything Baton still has to store for Run truth.

    Adapter tax on Rika

    Rika added @rika/relay-execution — a package whose job is translating product turns into Relay executions, Relay events into product events, Relay IDs into turn IDs, and re-registering agents every turn. The product contract ( ExecutionBackend) has ~20 methods because it mirrors Relay, not Rika.

    Symptom: Resident idle CPU dominated by scheduler polling. Resident RSS in the hundreds of MB. 208ms CPU per Relay event in benchmarks. Three vocabularies in every stack trace.

    Three vocabularies

    Layer Vocabulary Example identifiers
    Baton core Agent, Prompt, Tool, AgentEvent, suspension tool-call id, model attempt
    Relay Execution, Envelope, AddressBook, Workflow, Session execution_id, address_id, cursors
    Rika product Turn, Thread, ExecutionBackend, TurnEvent turnId, threadId, route snapshot

    Every feature required picking which vocabulary owns truth, then writing adapters to keep the others consistent. The replacement keeps durable facts in one place: Run + RunEvent + RunStore.

    Package responsibilities

    • @batonfx/core — Agent loop, tools, inline children, same-run handoffs, driver checkpoints, budgets, typed approval/suspension. Can run without Runtime.
    • @batonfx/runtime — Address, Message, finite Run, RunEvent, durable children, waits, signals, cancellation, joins, memory/SQLite/Postgres stores, worker claims.
    • Adapters — Transport (RunEvent SSE/WS), AG-UI, A2A, Rika TurnExecution. Projections only — no second event log.

    Decision log

    1. Clean break, not Relay v2

    We preserve product behavior (Rika turns, streaming, restart, subagents, review fan-out) but not Relay APIs, schemas, migrations, cursors, or runtime composition. Migrate Rika atomically, then delete Relay contracts and data paths.

    2. One logical cluster, defer federation

    Multi-cluster in v1 means: one logical cluster across many nodes, separate deployments isolated. Cross-cluster federation is deferred.

    3. Address = durable mailbox

    When a local agent address receives a message, it means:

    • Persist every envelope
    • Serialize delivery per address/conversation
    • Start or resume finite runs
    • Support correlated replies

    4. Baton-owned SQL kernel wins

    Not Effect Cluster as canonical scheduler. Not Rivet Engine. Not DBOS/Restate/Temporal as a second backend. A normalized six-table state machine Baton owns, with Effect SQL drivers for memory, SQLite, Postgres, and eventually MySQL.

    5. Strip Relay from Rika before building the Baton adapter

    Do not shape Baton to fit Relay's substrate. Rip Relay out, define TurnExecution from product needs only, ship test/unavailable layers, then compose Baton from first principles.

    6. Keep rika-server, delete resident naming

    Rika still needs a local server process (profile owner, SQLite owner, background work, multi-client, migrations). It becomes thin: composes @batonfx/runtime instead of Relay. Activity Monitor shows rika-server and rika-client.

    Alternatives we rejected

    Effect Cluster + Workflow

    rejected Would remain a second scheduler and second recovery journal.

    • RunnerStorage.acquire returns shard IDs, not monotonic ownership fences
    • Workflow engine correlates activities through process-local maps
    • No explicit unknown external outcome for replay safety
    • RPC chunks ≠ independent Run cursors for multiple clients
    • Baton would still need Run state, operations, waits, links, RunEvent history

    Rivet Actors

    rejected Strong ideas retained (keyed ownership, hibernation, append-before-notify).

    • Local use still requires Rivet Engine
    • Multi-node adds Postgres + NATS
    • No MySQL backend
    • Queue entries removed on receive, not ack-after-process
    • Realtime events are not a durable cursor log

    DBOS / Restate / Temporal

    rejected Best if we changed product constraints.

    • DBOS: best if Postgres-only forever
    • Restate: best if service-first forever
    • Neither preserves memory + SQLite + Postgres + MySQL + Effect streaming + exact RunEvent contract

    Three-table JSON blob design

    rejected Waits, links, timers, and worker claims need independent constraints and indexes across dialects.

    The SQL kernel

    Six normalized correctness tables. Migration metadata is separate.

    Table Purpose
    baton_lanes FIFO admission per (Address, Session)
    baton_runs Run identity, status, pinned AgentRef, fence
    baton_run_events Canonical append-only RunEvent stream
    baton_run_operations Driver operations for replay
    baton_run_waits Approvals, external waits, request/reply CAS
    baton_run_links Parent/child, fan-out membership 
    stateDiagram-v2
  [*] --> Pending: Message accepted
  Pending --> Running: Worker claims head
  Running --> Waiting: Suspend / approval / external wait
  Waiting --> Running: respond / signal / reply
  Running --> Completed: terminal success
  Running --> Failed: terminal failure
  Running --> Cancelled: cancel
  Waiting --> Cancelled: cancel

    Migration posture

    • SQLite: automatic migration at layer acquisition (embedded, single-process)
    • Postgres / MySQL: verify-only at startup; explicit predeploy plan/check/apply

    One event stream

    RunEvent extends AgentEvent with run lifecycle, waits, child links, handoffs. Strict per-Run sequence. Stable event IDs. Parent streams contain link/join/ terminal projection facts only — child detail stays in the child stream.

    Transport replacement: Drop SessionRegistry + parallel frame lifecycle. Direct RunEvent SSE/WebSocket with Last-Event-ID, typed CursorExpired, snapshot recovery, bounded subscriber queues, lag disconnect. No disconnect-implies-cancel.

    Durable driver inside the loop

    Every nondeterministic operation crosses DurableAgentDriver / DriverInterpreter:

    • Model attempts
    • Tool execution
    • Compaction (proactive + apply)
    • Memory recall / remember
    • Session sync, structured output
    • Suspension, resume, same-run handoff

    Each operation ends as succeeded, failed, or unknown. Unknown non-idempotent operations do not auto-retry.

    Honest guarantee: Once a Message is durably accepted, exactly one stable RunId is associated with its idempotency key. Run attempts may repeat. Committed state and terminal outcome are linearized once. External effects are effect-once only when the destination honors Baton's stable idempotency key.

    Process naming

    • rika-server — local profile server (bin/rika-server)
    • rika-client — CLI/TUI client
    • rika-client:<connectionId> — optional after handshake

    What Rika product packages keep owning

    • Thread, Turn, workspace policy, configuration
    • Product tools, terminal UX, transcript projection
    • Server lifecycle — not Baton, not Relay

    Non-negotiable invariants

    • One authority: RunStore only. No Cluster, Rivet, DBOS, Restate, Temporal as coequal paths.
    • Stable RunId: Survives restart, worker takeover, retry, approval, wait, cancel.
    • One stream per Run: Canonical RunEvent; adapters are projections.
    • FIFO without control deadlock: Lane per (Address, Session); control inputs bypass lane.
    • Fenced ownership: Stale worker commits zero rows after takeover.
    • Version pinning: Unsupported pinned versions fail typed — never silent behavior change.
