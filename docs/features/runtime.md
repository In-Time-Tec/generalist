# Runtime

`tenetkit/runtime` admits exact executions or addressed Messages into finite Runs, appends one canonical `RunEvent` stream per Run, and exposes `start`, `send`, `spawn`, `fanOut`, `awaitFanOut`, `steer`, `events`, `respond`, `respondApproval`, `signal`, `cancel`, `cancelSession`, `awaitSessionTerminal`, `inspect`, `inspectFanOut`, `snapshot`, finite `history`, finite `list`, `sessionEntry`, `resolveModelResponse`, and tree inspection. A blocking ask is not a Runtime primitive.

- `Address` is an opaque routing key bound to a pinned `ExecutableRef` through Layers. `Message` wraps Effect AI `Prompt` with idempotency, session/lane, and correlation fields and does not introduce a second content vocabulary.
- `start` admits an application-supplied exact `PinnedExecutable` without an address binding. It validates a complete, bounded set of immutable `{ pin, codec, version, payload }` registrations for every opaque model/capability pin and persists the catalog and root associations atomically with the Run. An optional bounded `initialChildren` set names child selections from the root's active Agent plus exact invocation, idempotency, prompt, session, and metadata sources. The root, initial children, links, registrations, and tree events commit as one admission; changed child sources conflict, and exact retries return the same root and child Run IDs. Registration payloads contain secret-free reconstruction data, not resolved credentials.
- A capability may pin the exact host-owned content its registration must reconstruct. `AgentManifest.NamedCapability.content` is an optional `{ codec, version, digest }` triple that participates in the manifest and executable digests, so changing pinned content changes the executable identity. Validation then requires the registration for that pin to match the declared codec and version and to digest to the declared digest; a drifted payload, a wrong codec, a wrong version, or an absent registration fails typed. One pin declared twice with identical content is accepted and with conflicting content fails; a capability without `content` stays opaque and unconstrained, exactly as before. `ExecutableRegistration.narrow` enforces the same rule against the active executable.
- `ExecutableResolver.resolve` receives the persisted Run reference, manifest, and root registration set. Application resolvers own codec interpretation, credential dereference, provider reconstruction, compaction/summary-model Layer composition, and scoped resource finalization. Agent resolutions may return exact services and static compaction run options; ExecutionHost accepts only the manifest's context window and reserve tokens and keeps prompt, history, checkpoint, continuation, identity, and budget authoritative. Recovery does not read application rows or current configuration; invalid, missing, and conflicting registrations fail typed without fallback. Static resolvers continue to accept addressed Runs with no registration set when their live executable is fully supplied.
- Ordinary admission is FIFO per `(Address, Session)`. Only the lane head is runnable. `respond`, `signal`, and `cancel` target an existing Run and bypass the lane so waiting work cannot deadlock successors.
- `cancelSession` requests cancellation for every root tree admitted under one Session, including descendants of prior roots. `awaitSessionTerminal` snapshots the Session's roots when called, then follows every Run in those trees until terminal with durable periodic reinspection as a missed-notification fallback. A host closing a Session must fence new root admission before calling it. Cancellation reconciliation fences stale local claims, repairs persisted cancellation-requested running states at store startup, and settles descendants before a cancelling ancestor.
- Exact duplicate idempotency keys return the same `RunReceipt`. A changed payload for the same key fails typed. `send.runId` optionally constrains admission to a caller-assigned stable identity; an idempotency replay or existing Run bound to another identity fails as `RunIdConflict`. First terminal event wins among completed, failed, and cancelled.
- `steer` persists an idempotent FIFO inbox entry for one nonterminal Run and returns its opaque `SteeringReceipt { entryId, sequence }`. An equivalent duplicate key returns the same receipt without a second acceptance; changed prompts fail as `SteeringConflict`. The Run journal records a reconstructable `SteeringAccepted` with the exact prompt, a `SteeringConsumed` with ordered entry ids and the consuming model-operation id, or a `SteeringDiscarded` with ordered entry ids and terminal reason. Admission and acceptance commit together; ExecutionHost reads pending entries without removing them and commits their consumed markers and fact atomically with the next model operation and DriverCheckpoint; terminalization commits any remaining accepted entries' disposition and discard fact. Core `SteeringDrained` remains separate aggregate loop telemetry. Completion either commits terminal state or reports pending steering in the same store transaction, then ExecutionHost continues from the canonical Session cursor.
- Each Run has one stream with stable `eventId` values and a strictly increasing per-Run sequence. Followers replay `sequence > cursor`, then follow live. Subscriber queues are bounded; lag and unavailable cursors fail typed without blocking the producer.
- `snapshot` atomically pairs `RunInspection` with its exclusive cursor, terminal-event-derived outcome, authoritative raw model-attempt usage, and running/applied/failed compaction states. Raw usage comes only from `ModelAttemptCompleted.usage` and `ModelAttemptFailed.providerUsage`; call, turn, and finish summaries are not usage facts. Duplicate attempt IDs deduplicate only when their facts agree, otherwise inspection fails as corrupt. No pricing or cost projection lives in Runtime.
- `RunEvent` is a strict producer schema composed from lifecycle schemas and core model telemetry. Completed and interrupted model-response events are reference-only; `resolveModelResponse` verifies their Session entry parent and digest before returning semantic content. Only payload fields that are intentionally dynamic, such as tool values and metadata, remain unknown.
- Wait resolution is durable. A typed `Approval` wait carries its stable approval ID plus the requested operation, capability, and encoded input. `Approval.approve` / `Approval.deny` are the caller-facing controls over `Runtime.respondApproval` and target exactly that request: an identical response is idempotent, a changed or mismatched response fails as `ApprovalMismatch`, and a request that is no longer known or pending fails as `ApprovalStale`. `Approved` continues the authorization path; `Denied`, `ToolResult`, and `Signal` are applied to the authoritative core suspension on re-entry rather than redispatching a resolved suspended call. Generic `respond` and unknown-operation `resolveOperation` remain separate controls.
- Parent streams persist child link and terminal projection only. Child detail remains in the child stream. `RunTree.history` and `RunTree.events` project an arbitrary-depth tree in one dense root order with one opaque, root-bound cursor. `RunTree.events` and finite `RunTree.watch` subscribe to coalesced root-tree change wakeups before replaying strictly after the cursor; memory and SQLite appends wake descendants immediately, while a one-second recovery probe covers a missed notification without making polling the normal delivery path. Each projected event carries authoritative root, Run, parent, invocation, and explicitly derivable model/tool call identities; the projection index references canonical event rows and is not a second lifecycle log.
- Every root pins one immutable `{ maxDepth, maxSubagents }` tree policy and has depth zero. Child depth is always derived as parent depth plus one. `maxDepth` bounds descendants, while `maxSubagents` is each parent's active direct-child capacity across singleton and group paths. Admission serializes under the parent lock and checks exact replay first. A request beyond current capacity is admitted durably with `queued` readiness rather than rejected; terminal and cancelled children become `settled`, release capacity, and transactionally promote the oldest eligible queued children. `maxSubagents: 0` rejects direct framework admission as `ChildLimitExceeded` and removes hosted child tools. `ChildDepthExceeded` and `ChildLimitExceeded` carry the parent, root, depth, requested/current, and limit facts.
- Durable child and fan-out requests name semantic child selections, not executable refs. Each version-2 Agent manifest pins a selection-name allowlist, while its finite version-2 executable manifest pins one global `profiles: [{ selection, agent }]` registry and every referenced Agent entry. Under the parent admission lock, Runtime authorizes the requested name against the active Agent's allowlist, resolves it through the persisted profile registry, and persists a child ref with the parent's executable pin. Profiles may mutually or self-select at any allowed Runtime depth without unrolling entries or introducing digest cycles. Every `ChildLinked` event carries that canonical `selection`, prompt, derived child depth, and any explicit member key, display label, and structured parent-operation origin alongside the invocation and child Run IDs. Fan-out inspection persists the same member identity without requiring invocation-ID parsing. Missing or unauthorized selections fail as `ChildSelectionMissing` before any child, link, event, or fan-out row is written. Address bindings and the executable resolver do not grant child authority.
- `RunTree.inspect` atomically folds every Run under a root in deterministic discovery order, with authoritative parent/invocation/outcome, tree-wide raw usage and compactions, and exact active Run IDs. `Terminal` means every discovered Run has a matching canonical terminal event and is stable because terminal parents cannot spawn. `RunTree.awaitTerminal` inspects first, follows tree events strictly after that cursor, and re-inspects on discovery or terminal transitions, closing the inspect-to-subscribe race without caller-side child polling.
- A compaction pass emits `CompactionStarted` before work. No-change passes emit `CompactionSkipped`; changed Session-backed passes commit `CompactionApplied` atomically with their deterministic checkpoint and publish that exact event live after commit. `CompactionApplied` carries the authoritative `CompactionCommit`; work or pre-commit application failure and interruption emit `CompactionFailed` and never `Applied`.
- A compacting Agent manifest requires both its compaction-service and summary-model registrations. The compaction payload is the bounded secret-free `{ keepRecentTokens, strategyIdentity, summaryPromptIdentity }` policy; the summary model remains an opaque model registration interpreted by the application resolver. The manifest alone owns `contextWindow` and `reserveTokens`.
- `fanOut` admits one immutable ordered member set under a parent Run. Every selection resolves atomically under the parent lock, and exact resolved refs participate in the idempotency digest while the public request remains selection-based. The `(parentRunId, idempotencyKey)` pair returns one stable aggregate and deterministic child Run IDs; changed bindings, member order, or policy fail as `FanOutConflict`. A group larger than available parent capacity remains one atomic admission: eligible members are `ready`, excess members are `queued`, and terminal settlement promotes queued members. Optional `concurrency` may further narrow the group's active members but never exceeds the root-pinned parent capacity. Member readiness is persisted independently from ordered all-settled status and result.
- Join rules are `AllSuccess`, `AllSettled`, `FirstSuccess`, `Quorum`, and `BestEffort`. Remainder rules are `await`, `request-cancel`, and `abandon`; `terminate` fails as `FanOutRemainderUnsupported` because no current host can prove external-effect termination. Child terminal state, member outcome, join decision, and next promotion commit in one store transaction. Parent cancellation cancels and settles every owned member before the parent terminal event.
- `run_operations` records model/tool/memory/compaction/send/structured-output work with requested/running/succeeded/failed/unknown. Expired non-idempotent running operations become `unknown`, put an ordinary Run in `needs-resolution`, and are not worker-claimable. Cancellation is authoritative over Run lifecycle: an unknown committed after cancellation leaves the Run `cancelling`, and cancellation of an already `needs-resolution` Run may become terminal while the operation remains truthfully `unknown`. `Runtime.resolveOperation` atomically records a schema-backed `Succeeded`, `Failed`, or `Retry` decision without changing the driver checkpoint, is idempotent for the exact key and decision, and fails changed decisions as `OperationResolutionConflict`. A resolved Run becomes claimable only after that decision commits; replay consumes a persisted success or failure without redispatch, while `Retry` explicitly returns the operation to requested. Pure or provider-idempotent operations may return to requested automatically.
- `RunStore.layerMemory` / `Runtime.layerMemory` are ephemeral in-memory stores. They preserve admission, idempotency, FIFO, control-input, wait/signal, cancellation, child-link, operation, and replay contracts, but release loses all state.
- `RunStore.layerSqlite` / `Runtime.layerSqlite` are durable single-process SQLite stores. Capability reports `durability: "durable"`, `backend: "sqlite"`, `multiWorker: false`. Multi-worker configuration fails typed as `MultiWorkerUnsupported`.
- Memory and SQLite Runtime layers own one scoped local scheduler. It claims unowned Runs and its own recovered claims, executes roots and children through `ExecutionHost`, and never requires an application claim loop. Every host exit finalizes the resolver and execution scope, then idempotently releases only its exact `(runId, ownerId, attemptFence)` claim before removing the process-local active marker. A stale release cannot clear a replacement claim, while an interrupted nonterminal Run becomes immediately reclaimable without stealing foreign ownership.
- The scheduler reconciles settled children by paging waiting parents, not by scanning terminal Runs, so a child that settles in a different order than it was created still resumes its parent and an idle tick costs three bounded list calls with no decodes. Per-tick cost scales with waiting parents and their children rather than with the terminal backlog: a parent holding a wait no terminal child can answer, such as a long human approval, re-reads its settled children every tick, bounded by the 32-parent reconcile window. A per-parent-and-wait memo is the remedy if that cost ever matters. The waiting page advances through a cursor, and a parent's open-wait identity is re-read before any resume; the store independently rejects a resume against an already-responded or non-active wait, so those scheduler-side checks are defense in depth rather than the authority, and deleting them leaves the suite green.
- `ChildRuns.tool` and `ChildRuns.route` keep `run_child` as the blocking dependent-singleton path. The primary grouped model contract is `run_child_group`: one replay-idempotent call atomically admits an exact ordered `AllSettled`/`await` fan-out, durably queues members beyond active capacity, and suspends the same parent until every member settles. Join reconciliation commits complete, untruncated results in admission order into that tool's suspension resolution, closes the wait without an application response, and resumes the parent once across restart, completion-before-suspension, and out-of-order mixed outcomes. Parent cancellation recursively cancels members without resuming the tool. `start_child_group` and `await_child_group` remain lower-level detached operations. `ChildRuns.makeTools` derives model-visible selection enums from the active Agent's declared child authority while the store remains authoritative. ExecutionHost installs the blocking tools only when the persisted Run has `depth < treePolicy.maxDepth` and `activeChildCount < treePolicy.maxSubagents`; a leaf, zero-capacity, or currently full parent retains its ordinary Agent tools but does not advertise child tools. Admission and transactional promotion remain the concurrency backstop.
- Core `BudgetLimits.childRuns` and `BudgetLimits.depth` govern only process-local inline `AgentTool` nesting. Runtime child tools and framework admission paths do not consult them; the Runtime fallback Agent budget omits both fields. The root-pinned `TreePolicy` is the sole depth and per-parent active direct-child authority for durable Run trees.
- SQLite acquires with WAL, foreign keys, and `BEGIN IMMEDIATE` transactions. Schema migration runs automatically at Layer acquisition through Effect SQL migrations, then verifies dirty flag, checksum, and supported version. Dirty, checksum mismatch, unsupported forward version, and migration failure are typed schema errors.
- `Runtime.layerPostgres` is the durable multi-worker PostgreSQL store. Capability reports `durability: "durable"`, `backend: "postgres"`, `multiWorker: true`. Correctness reuses SQLite's relational state machine, including dedicated `baton_fan_outs` and `baton_fan_out_members` tables, plus `baton_schema_meta` / migrator metadata, with Postgres types (`BOOLEAN`, `TIMESTAMPTZ`) and claim columns (`owner_worker_id`, `lease_expires_at`, monotonic `attempt_fence`).
- PostgreSQL Runtime startup is verify-only: typed `SchemaUpgradeRequired`, `SchemaDirty`, `SchemaChecksumMismatch`, and `SchemaVersionUnsupported` failures. Predeploy jobs use `RunSchema.plan`, `RunSchema.check`, and `RunSchema.apply`. Runtime credentials must not need DDL. The current schema is one baseline version 1; apply creates an absent schema and never upgrades an older layout.
- Multi-worker ready-run claims use `FOR UPDATE SKIP LOCKED`, database-time leases, monotonic attempt epochs, lease refresh/recovery, stale-owner zero-row commits (`StaleClaim`), only-head-ready lane promotion, and concurrency-proportional claim plans via `RunClaims` / `RuntimeWorker`.
- Event append batches allocate per-Run sequences with `UPDATE … RETURNING` (no `MAX` races). PostgreSQL `LISTEN`/`NOTIFY` is only a coalesced pointer hint; replay-after-cursor remains authoritative, and bounded recovery probes cover missed hints so followers on different Runtime instances observe identical history.
- The baseline schema includes one root counter and tree event index. New events receive their root-relative position transactionally when appended.
- For Agents, `ExecutionHost` reconstructs the pinned core Agent and DriverCheckpoint, provides a fenced `DriverJournalService`, persists each operation before dispatch, maps Agent events into RunEvent, and commits suspension or terminal state. A failed active operation is durably settled before the Run terminal event, including deferred Program-child failure after resolver finalizers. `RuntimeWorker.layerWorker` claims ready PostgreSQL Runs and executes them through this host.
- When a retryable model stream failure escapes after a completed turn, `ExecutionHost` starts at most two more execution attempts in the same Run. Each attempt receives the canonical Session projection, continuation, and DriverCheckpoint; completed child and tool operations stay journaled and are not dispatched again. Attempts keep the Run ID, append `RunAttemptStarted`, preserve the worker fence, and terminalize with the original typed Runtime failure after attempt 3.
- `ExecutionHost` dispatches tagged Agent and Program resolutions only after resolver attestation matches the persisted executable closure. Program tool calls and logs use stable named operation keys in `run_operations`; matching completed calls replay, changed inputs diverge, and unknown non-idempotent calls remain blocked for explicit resolution. Durable Program Agent runs, maps, and fan-outs atomically reserve the Program operation and budget with immutable child admission. Child terminal reconciliation closes the Program wait and makes the parent claimable without an application resume call.
- Opaque canonical JSON text is stored with schema codecs; correctness queries do not inspect JSON payloads.
- `Runtime.layerMysql` is the durable multi-worker MySQL 8+ store. It has the same relational state machine, verify-only startup, database-time leases, monotonic attempt fences, stale-owner rejection, bounded fan-out claims, and lane-head claims as PostgreSQL. `MysqlRunSchema.plan`, `check`, `apply`, and `markDirty` own predeploy schema work; `apply` serializes creation of the version 1 baseline with a named migration lock.
- MySQL transactions run at `READ COMMITTED`. Claims use bounded candidate scans plus primary-key `FOR UPDATE SKIP LOCKED`, and deadlocks retry the whole transaction. Writes do not rely on `RETURNING`; rows are read after fenced updates, booleans decode from `TINYINT(1)`, and timestamp strings decode at the store boundary.
- MySQL event delivery is polling-backed for local and cross-process followers. Each subscription owns its poller scope, registers before polling begins, and advances from committed durable history after the exclusive cursor.
