# Runtime

`generalist/runtime` is the Worker-safe Runtime contract and memory implementation. It admits exact executions or addressed Messages into finite Runs, appends one canonical `RunEvent` stream per Run, and exposes `start`, `admit`, `activate`, `send`, `spawn`, `fanOut`, `awaitFanOut`, `steer`, `events`, `acknowledge`, `acknowledged`, `respond`, `respondApproval`, `signal`, `cancel`, `cancelSession`, `awaitSessionTerminal`, `inspect`, `inspectFanOut`, `snapshot`, finite `history`, finite `list`, `sessionEntry`, `resolveModelResponse`, and `RunTree` checkpoint/replay. A blocking ask is not a Runtime primitive. Bun SQLite, SQL claims, and hosted SQL worker loops remain explicit opt-in subpaths.

- `Address` is an opaque routing key bound to a pinned `ExecutableRef` through Layers. `Message` wraps Effect AI `Prompt` with idempotency, session/lane, and correlation fields and does not introduce a second content vocabulary.
- `start` admits an application-supplied exact `PinnedExecutable` without an address binding. It validates a complete, bounded set of immutable `{ pin, codec, version, payload }` registrations for every opaque model/capability pin and persists the catalog and root associations atomically with the Run. An optional bounded `initialChildren` set names child selections from the root's active Agent plus exact invocation, idempotency, prompt, session, and metadata sources. The root, initial children, links, registrations, and tree events commit as one admission; changed child sources conflict, and exact retries return the same root and child Run IDs. Registration payloads contain secret-free reconstruction data, not resolved credentials.
- `admit` is the staged form for exactly one root. It validates and persists the same exact executable, registrations, Session, idempotency key, optional caller-supplied Run ID, and payload as `start`, but leaves the parentless Run `queued` with only `RunAccepted`; workers, schedulers, models, and tools cannot claim it. Exact retries return the same `RunReceipt`, including after activation or cancellation, while changed payloads and conflicting Run IDs retain the existing typed failures. `activate({ runId })` and `cancel({ runId })` serialize in the authoritative store. Activation appends `RunAttemptStarted` exactly once only when it wins on an uncancelled queued root and returns the current `RunInspection`; duplicate activation and activation after cancellation are idempotent. A cancellation that wins terminalizes the queued Run as `cancelled`, and later activation cannot execute it. `start` remains the immediate composed convenience and preserves initial-child and initial-fan-out admission.
- A capability may pin the exact host-owned content its registration must reconstruct. `AgentManifest.NamedCapability.content` is an optional `{ codec, version, digest }` triple that participates in the manifest and executable digests, so changing pinned content changes the executable identity. Validation then requires the registration for that pin to match the declared codec and version and to digest to the declared digest; a drifted payload, a wrong codec, a wrong version, or an absent registration fails typed. One pin declared twice with identical content is accepted and with conflicting content fails; a capability without `content` stays opaque and unconstrained, exactly as before. `ExecutableRegistration.narrow` enforces the same rule against the active executable.
- `ExecutableResolver.resolve` receives the persisted Run reference, manifest, and root registration set. Application resolvers own codec interpretation, credential dereference, provider reconstruction, compaction/summary-model Layer composition, and scoped resource finalization. Agent resolutions may return exact services and static compaction run options; RunExecutor accepts only the manifest's context window and reserve tokens and keeps prompt, history, checkpoint, continuation, identity, and budget authoritative. Recovery does not read application rows or current configuration; invalid, missing, and conflicting registrations fail typed without fallback. Static resolvers continue to accept addressed Runs with no registration set when their live executable is fully supplied.
- Ordinary root admission is FIFO per Session across all addresses. Only the Session lane head may acquire the Session write claim; address and idempotency identities remain separate. Different Sessions and child Sessions remain independently runnable. `respond`, `signal`, and `cancel` target an existing Run and bypass the lane so waiting work cannot deadlock successors.
- `cancelSession` requests cancellation for every root tree admitted under one Session, including descendants of prior roots. `awaitSessionTerminal` snapshots the Session's roots when called, then follows every Run in those trees until terminal with durable periodic reinspection as a missed-notification fallback. A host closing a Session must fence new root admission before calling it. `cancel` and `cancelSession` durably close operation admission before delivery, recursively mark active descendants, and settle descendants before a cancelling ancestor. Successful return means the durable request was admitted and interrupt delivery was requested from any process-local owner; it does not mean `RunCancelled`. Callers observe terminality through `inspect`, events, tree following, or the terminal waiting surfaces. Process-local hosted work remains owned until its actual exit. `Generalist.Runtime.cancel` records durable request admission; its `localExit` child span records interrupt delivery, grace expiry, and actual exit acknowledgement. Grace expiry is observational and does not release the owner. Durable `RunCancellationRequested` and `OperationUnknown` events retain request and unknown-state evidence. Every admitted tool operation whose selected concrete `ToolExecutor` exposes `cancel` remains in durable `cancelling` state until that same route returns `Cancelled` or `AlreadyTerminal`; callback failure, interruption, process loss, and lease expiry leave it reclaimable for same-identity redelivery without another application cancellation request. An ambiguous non-cancellable `never` operation becomes `unknown` and leaves the Run in `needs-resolution`, even when cancellation was requested. RunExecutor shutdown and lease loss by themselves only use ordinary operation recovery and never request semantic cancellation.
- Exact duplicate idempotency keys return the same `RunReceipt`. A changed payload for the same key fails typed. `send.runId` optionally constrains admission to a caller-assigned stable identity; an idempotency replay or existing Run bound to another identity fails as `RunIdConflict`. First terminal event wins among completed, failed, and cancelled.
- `steer` persists an idempotent FIFO inbox entry for one nonterminal Run and returns its opaque `SteeringReceipt { entryId, sequence }`. Direct admission is finite at 64 pending entries and 1 MiB of canonical encoded prompts per Run; overload fails as `Steering.InboxFull`, and Runtime never holds a durable request open for backpressure. An equivalent duplicate key is checked before capacity and returns the same receipt without a second acceptance; changed prompts fail as `SteeringConflict`. Addressed mailbox delivery remains governed by its own finite mailbox limits. The Run journal records a reconstructable `SteeringAccepted` with the exact prompt, a `SteeringConsumed` with ordered entry ids and the consuming model-operation id, or a `SteeringDiscarded` with ordered entry ids and terminal reason. Admission and acceptance commit together; RunExecutor reads pending entries without removing them and commits their consumed markers and fact atomically with the next model operation and DriverCheckpoint; terminalization commits any remaining accepted entries' disposition and discard fact. Core `SteeringDrained` remains separate aggregate loop telemetry. Completion either commits terminal state or reports pending steering in the same store transaction, then RunExecutor continues from the canonical Session cursor.
- Each Run has one stream with stable `eventId` values and a strictly increasing per-Run sequence. Followers replay `sequence > cursor`, then follow live. Subscriber queues are bounded; lag and unavailable cursors fail typed without blocking the producer.
- Each Run also has one Runtime-global durable host processed-through point. `acknowledge({ runId, sequence })` accepts only `-1` or the sequence of an existing committed `TurnCompleted` event, advances monotonically, and treats the same or an older valid boundary as a no-op. Malformed and non-boundary values fail as `AckInvalid`; a sequence beyond the latest committed cycle fails as `AckBeyondCommitted`. `acknowledged(runId)` returns the stored point or `{ runId, sequence: -1 }`. After restart, a host reads that point and passes its sequence to `events({ runId, cursor })` to replay exactly the unprocessed tail. Hosts that never acknowledge retain full replay from `-1`.
- `snapshot` atomically pairs `RunInspection` with its exclusive cursor, terminal-event-derived outcome, authoritative raw model-attempt usage, and running/applied/failed compaction states. Raw usage comes only from `AttemptCompleted.usage` and `AttemptFailed.providerUsage`; call, turn, and finish summaries are not usage facts. Duplicate attempt IDs deduplicate only when their facts agree, otherwise inspection fails as corrupt. No pricing or cost projection lives in Runtime.
- `RunEvent` is a strict producer schema composed from lifecycle schemas and core model telemetry. Completed and interrupted model-response events are reference-only; `resolveModelResponse` verifies their Session entry parent and digest before returning semantic content. Only payload fields that are intentionally dynamic, such as tool values and metadata, remain unknown.
- Wait resolution is durable and plural. One keyed row `(runId, waitId)` is the only mutable authority for immutable reason and identity, open or terminal status, exact schema-decoded resolution, and timestamps. Open waits are inspected in model-authored order. Every close path conditionally changes exactly one row from `open` to terminal before its one durable event; resolving one wait leaves siblings open. An identical duplicate generic response is read-only success, a conflicting duplicate is `ResponseConflict`, and terminal history cannot reopen. A typed `Approval` wait carries its stable approval ID plus the requested operation, capability, and encoded input. `Approval.approve` / `Approval.deny` target exactly that request: an identical response is idempotent, a changed or mismatched response fails as `ApprovalMismatch`, and a request that is no longer known or pending fails as `ApprovalStale`. Generic `respond` and unknown-operation `resolveOperation` remain separate controls.
- Parent streams persist child link and terminal projection only. Child detail remains in the child stream. `RunTree.checkpoint(rootRunId)` atomically returns `{ inspection, cursor }` for the arbitrary-depth tree. The inspection folds Runs in deterministic discovery order with authoritative parent/invocation/outcome, tree-wide raw usage and compactions, and exact active Run IDs; it does not copy canonical events. `Terminal` means every discovered Run has a matching canonical terminal event and is stable because terminal parents cannot spawn.
- `RunTree.replay({ rootRunId, cursor, limit })` reads canonical events strictly after the opaque root-bound cursor in dense root order. `limit` is an integer from 1 through 1000. A page cursor names its last returned event, or remains the requested cursor for an empty page; `hasMore` is true exactly when at least one retained committed event remains after that page. Repeating the same read without an intervening append is side-effect free and returns the same page. Each projected event carries authoritative root, Run, parent, invocation, and explicitly derivable model/tool call identities; the projection index references canonical event rows and is not a second lifecycle log.
- Malformed cursors fail as `TreeCursorInvalid`; a cursor for another root fails as `TreeCursorRootMismatch`; an uncommitted position fails as `TreeCursorFuture` with `latestCursor`; a position older than retained replay fails as `TreeCursorExpired` with `earliestCursor`; and an invalid bound fails as `TreeReplayLimitInvalid`. Current memory, SQLite, PostgreSQL, and MySQL drivers retain the full tree projection for the root lifetime. The expiry contract permits a driver to shorten that retention without changing replay semantics. A host that needs a new point-in-time baseline after expiry reacquires `RunTree.checkpoint`; cursors are observation positions, not durable host acknowledgements.
- `RunTree.events` and finite `RunTree.watch` subscribe to coalesced root-tree change wakeups before replaying strictly after the cursor, so handing off a checkpoint cursor cannot open a snapshot/live gap. Memory and SQLite appends wake descendants immediately, while a one-second recovery probe covers a missed notification without making polling the normal delivery path.
- Every root pins one immutable `{ maxDepth, maxSubagents }` tree policy and has depth zero. Child depth is always derived as parent depth plus one. `maxDepth` bounds descendants, while `maxSubagents` is each parent's active direct-child capacity across singleton and group paths. Admission serializes under the parent lock and checks exact replay first. A request beyond current capacity is admitted durably with `queued` readiness rather than rejected; terminal and cancelled children become `settled`, release capacity, and transactionally promote the oldest eligible queued children. `maxSubagents: 0` rejects direct framework admission as `ChildLimitExceeded` and removes hosted child tools. `ChildDepthExceeded` and `ChildLimitExceeded` carry the parent, root, depth, requested/current, and limit facts.
- `ExternalChildStore` owns both halves of cross-partition children over `ExternalRunRef { partition, runId }`; applications own only transport and partition placement. Browser and Worker consumers import the protocol from `generalist/runtime/external-child-placement` and the service from `generalist/runtime/external-child-store` without loading the Bun SQLite Runtime graph. On the parent partition, `reserve` atomically records the immutable ref, invocation, request/executable digests, capacity, current execution claim, and optional parent suspension before transport dispatch. `acknowledge`, `cancel`, and `settle` are idempotent; settlement may arrive before acknowledgement, rejects divergent identity or outcome, closes only the placement-owned wait, releases capacity, and lets authoritative settlement converge parent cancellation without fabricating a remote result.
- On the child partition, `admitRoot` atomically creates an independently addressable depth-zero root plus its external parent link. Its supplied `ref.runId` is the Run ID, its Message Session is the stable conversation identity, and `ExternalChildPlacement.executableDigest` verifies the exact pinned executable. Admission is replay-idempotent only for identical parent/ref/request/executable/root facts. The root remains `queued` and cannot be claimed until idempotent `activateRoot`; `cancelRoot` is authoritative before or after activation. `inspectRoot` preserves the link across restart. Once terminal, `rootSettlement` replays the same `{ settlementId: outcome.eventId, outcome }` until exact `acknowledgeRootSettlement`; a wrong terminal identity conflicts. This is at-least-once transport with exactly-once parent application, not a generic router or a second lifecycle. Memory and single-partition SQLite provide the capability; PostgreSQL and MySQL do not advertise it.
- Durable child and fan-out requests name semantic child selections, not executable refs. Each version-2 Agent manifest pins a selection-name allowlist, while its finite version-2 executable manifest pins one global `profiles: [{ selection, agent }]` registry and every referenced Agent entry. Under the parent admission lock, Runtime authorizes the requested name against the active Agent's allowlist, resolves it through the persisted profile registry, and persists a child ref with the parent's executable pin. Profiles may mutually or self-select at any allowed Runtime depth without unrolling entries or introducing digest cycles. Every `ChildLinked` event carries that canonical `selection`, prompt, derived child depth, and any explicit member key, display label, and structured parent-operation origin alongside the invocation and child Run IDs. Fan-out inspection persists the same member identity without requiring invocation-ID parsing. Missing or unauthorized selections fail as `ChildSelectionMissing` before any child, link, event, or fan-out row is written. Address bindings and the executable resolver do not grant child authority.
- `RunTree.awaitTerminal` checkpoints first, follows tree events strictly after that cursor, and checkpoints again on discovery or terminal transitions, closing the checkpoint-to-subscribe race without caller-side child polling.
- A compaction pass emits `CompactionStarted` before work. No-change passes emit `CompactionSkipped`; changed Session-backed passes commit `CompactionApplied` atomically with their deterministic checkpoint and publish that exact event live after commit. `CompactionApplied` carries the authoritative `CompactionCommit`; work or pre-commit application failure and interruption emit `CompactionFailed` and never `Applied`.
- A compacting Agent manifest requires both its compaction-service and summary-model registrations. The compaction payload is the bounded secret-free `{ keepRecentTokens, strategyIdentity, summaryPromptIdentity }` policy; the summary model remains an opaque model registration interpreted by the application resolver. The manifest alone owns `contextWindow` and `reserveTokens`.
- `fanOut` admits one immutable ordered member set under a parent Run. Every selection resolves atomically under the parent lock, and exact resolved refs participate in the idempotency digest while the public request remains selection-based. The `(parentRunId, idempotencyKey)` pair returns one stable aggregate and deterministic child Run IDs; changed bindings, member order, or policy fail as `FanOutConflict`. A group larger than available parent capacity remains one atomic admission: eligible members are `ready`, excess members are `queued`, and terminal settlement promotes queued members. Optional `concurrency` may further narrow the group's active members but never exceeds the root-pinned parent capacity. Member readiness is persisted independently from ordered all-settled status and result.
- Join rules are `AllSuccess`, `AllSettled`, `FirstSuccess`, `Quorum`, and `BestEffort`. Remainder rules are `await`, `request-cancel`, and `abandon`; `terminate` fails as `FanOutRemainderUnsupported` because no current host can prove external-effect termination. Child terminal state, member outcome, join decision, and next promotion commit in one store transaction. Parent cancellation cancels and settles every owned member before the parent terminal event.
- `run_operations` records model/tool/memory/compaction/send/structured-output work with requested/running/cancelling/cancelled/succeeded/failed/unknown. Every claimed host reconciles all operations left `running` by the prior owner in one fenced store transaction before resolver, Program, or Agent entry: pure and provider-idempotent operations return to `requested`, while a `never` operation becomes `unknown`, emits `OperationUnknown`, and puts an ordinary Run in `needs-resolution` without starting another turn. Recovery retries are idempotent. Explicit cancellation promotes admitted cancellable tool operations from requested, running, or unknown to `cancelling`; a definitive executor acknowledgement then records cancelled or the reported terminal outcome before `RunCancelled` may commit. Non-cancellable unknown operations retain their truthful unknown state. `Runtime.resolveOperation` atomically records a schema-backed `Succeeded`, `Failed`, or `Retry` decision without changing the driver checkpoint, is idempotent for the exact key and decision, and fails changed decisions as `OperationResolutionConflict`. A Run with several unknown operations stays in `needs-resolution` until all are resolved; replay then consumes each persisted success or failure through normal Agent tool completion and Session append without redispatch, while `Retry` explicitly returns the operation to requested.
- `RunStore.layerMemory` / `Runtime.layerMemory` are ephemeral in-memory stores. They preserve admission, idempotency, FIFO, control-input, wait/signal, cancellation, child-link, operation, and replay contracts, but release loses all state.
- `SqliteRunStore.layerSqlite` / `SqliteRuntime.layerSqlite`, imported as `RunStore` / `Runtime` from `generalist/runtime/sqlite-bun`, are durable single-process SQLite stores. The generic `generalist/runtime` entrypoint does not load or require the SQLite peer. Capability reports `durability: "durable"`, `backend: "sqlite"`, `multiWorker: false`. Multi-worker configuration fails typed as `MultiWorkerUnsupported`.
- `makeRuntimeActor` from `generalist/rivet/actors` binds that same SQLite lifecycle kernel to one Rivet Actor per Runtime partition. Actor-local SQLite is the sole mutable authority. Actions use existing Runtime inputs and outputs; one-shot schedules and a persistent cron are only post-commit doorbells over durable activation rows. Every wake atomically advances an actor-local host-incarnation row, recovers stale Run and Session claims under that new owner, backfills activation rows, and drains a bounded page. Pinned Rivet engine generation checks reject a delayed prior-incarnation page commit after replacement, while Generalist recovery leaves interrupted non-idempotent work `unknown` and never redispatches it. The package uses raw `rivetkit@2.3.10`, not the incompatible Rivet Effect SDK, and wraps Promise, interruption, transaction, and resource ownership only at the actor SQL boundary.
- Memory and SQLite Runtime layers own one scoped local scheduler. It claims unowned Runs and its own recovered claims, executes roots and children through `RunExecutor`, and never requires an application claim loop. Every host exit finalizes the resolver and execution scope, then idempotently releases only its exact `(runId, ownerId, attemptFence)` claim before removing the process-local active marker. A stale release cannot clear a replacement claim, while an interrupted nonterminal Run becomes immediately reclaimable without stealing foreign ownership.
- The scheduler reconciles settled children by paging waiting parents, not by scanning terminal Runs, so children that settle out of order each close only their owned wait and an idle tick costs three bounded list calls with no decodes. Per-tick cost scales with waiting parents and their children rather than with the terminal backlog. The waiting page advances through a cursor, and each owned keyed wait is re-read before a resume; the store's conditional open-to-terminal transition remains the authority.
- `ChildRuns.tool` and `ChildRuns.route` keep `run_child` as the blocking dependent-singleton path. The primary grouped model contract is `run_child_group`: one replay-idempotent call atomically admits an exact ordered `AllSettled`/`await` fan-out, durably queues members beyond active capacity, and suspends the same parent until every member settles. Join reconciliation commits complete, untruncated results in admission order into that tool's suspension resolution, closes the wait without an application response, and resumes the parent once across restart, completion-before-suspension, and out-of-order mixed outcomes. Parent cancellation recursively cancels members without resuming the tool. `start_child_group` and `await_child_group` remain lower-level detached operations. `ChildRuns.makeTools` derives model-visible selection enums from the active Agent's declared child authority while the store remains authoritative. RunExecutor installs the blocking tools only when the persisted Run has `depth < treePolicy.maxDepth` and `activeChildCount < treePolicy.maxSubagents`; a leaf, zero-capacity, or currently full parent retains its ordinary Agent tools but does not advertise child tools. Admission and transactional promotion remain the concurrency backstop.
- Core `BudgetLimits.childRuns` and `BudgetLimits.depth` govern only process-local inline `AgentTool` nesting. Runtime child tools and framework admission paths do not consult them; the Runtime fallback Agent budget omits both fields. The root-pinned `TreePolicy` is the sole depth and per-parent active direct-child authority for durable Run trees.
- SQLite acquires with WAL, foreign keys, and `BEGIN IMMEDIATE` transactions. Schema creation runs automatically at Layer acquisition, then verifies dirty flag, checksum, and supported version. The schema is one baseline, migration 1 `generalist_runtime` at version 4, created in a single transaction; there is no upgrade path from an older layout. Dirty, checksum mismatch, old or future versions, and migration failure are typed schema errors.
- `layer(options)` from `generalist/pg` is the durable multi-worker PostgreSQL store. URL options acquire the client; client-backed options use a caller-supplied Effect `PgClient`. Capability reports `durability: "durable"`, `backend: "postgres"`, `multiWorker: true`. A host using the same client may compose its SQL writes with public staged Runtime admission inside one `SqlClient.withTransaction`; Runtime nesting uses that exact transaction service and its savepoints. Correctness reuses SQLite's relational state machine, including dedicated `generalist_fan_outs` and `generalist_fan_out_members` tables, plus `generalist_schema_meta` / migrator metadata, with Postgres types (`BOOLEAN`, `TIMESTAMPTZ`) and claim columns (`owner_worker_id`, `lease_expires_at`, monotonic `attempt_fence`).
- PostgreSQL Runtime startup is verify-only: typed `SchemaUpgradeRequired`, `SchemaDirty`, `SchemaChecksumMismatch`, and `SchemaVersionUnsupported` failures. Predeploy jobs use `RuntimeSchema.plan`, `RuntimeSchema.check`, and `RuntimeSchema.apply`. Runtime credentials must not need DDL. The current schema is one baseline version 4; apply creates an absent schema and never upgrades an older layout.
- Multi-worker ready-run claims use `FOR UPDATE SKIP LOCKED`, database-time leases, monotonic Run attempt fences, and a storage-issued Session-global monotonic writer epoch bound to the exact Run, worker, and Run fence. Every Session mutation validates that full binding before side effects or exact-retry success; release, suspension, terminal settlement, lease takeover, and exclusive recovery revoke it without resetting the epoch. Lease refresh/recovery, stale-owner zero-row commits (`StaleClaim` / `StaleSessionClaim`), only-head-ready Session-lane promotion, and concurrency-proportional claim plans remain under `RunClaims` and `RuntimeWorker.layer` from the exact adapter SPI `generalist/runtime/sql-driver`. `RunClaims.changes` is a lossy doorbell that emits once after subscription is ready; PostgreSQL backs it with a scoped `LISTEN` connection. The worker subscribes before its startup catch-up, coalesces wakeups, drains durable claims until empty or saturated, reacquires a failed listener, and retains a slow durable fallback sweep for missed notifications and lease expiry.
- Event append batches allocate per-Run sequences with `UPDATE … RETURNING` (no `MAX` races). PostgreSQL `LISTEN`/`NOTIFY` is only a coalesced pointer hint and executes on the active transaction connection, so PostgreSQL releases it after the outermost commit and discards it on rollback. Replay-after-cursor remains authoritative, and bounded recovery probes cover missed hints so followers on different Runtime instances observe identical history.
- SQL Runtime telemetry has one stable semantic boundary: `Generalist.Runtime.sqlTransition` spans carry backend, transition, bounded Run/Operation identity, operation kind, and `committed`, `exact-retry`, `divergent-retry`, `stale-claim`, or `rolled-back` outcome. Nested Effect SQL `sql.execute` spans retain exact per-transition statement counts and PostgreSQL Migrator lock timing; `Generalist.Runtime.sqlLock`, `Generalist.Runtime.sqlMigrationLock`, and `Generalist.Runtime.sqlReplay` spans expose semantic lock acquisition, MySQL predeploy named-lock wait, and authoritative replay without logging SQL parameters or durable payloads. Corresponding `generalist_runtime_sql_*` metrics cover transition duration/outcome, ready-claim batch/takeover, semantic and MySQL migration lock duration, local wakeups versus durable replay count/duration, subscriber sequence lag/overflow, schema version/checksum/status, and MySQL deadlock retry/exhaustion. Exclusive SQLite hosts additionally record activation drain size/duration/outcome/rearm and incarnation recovery duration/count. Metric attributes stay bounded to backend, transition, lock kind, schema identity, and fixed outcome; Run and Operation identifiers remain trace-only. Session/model content, checkpoints, tool payloads, and raw SQL parameters are never telemetry attributes.
- The baseline schema includes one root counter and tree event index. New events receive their root-relative position transactionally when appended.
- For Agents, `RunExecutor` first asks the authoritative store to reconcile stale running operations under the current attempt fence, and enters resolution only when that preflight remains runnable. It then reconstructs the pinned core Agent and DriverCheckpoint, provides a fenced `DriverJournal`, persists each operation before dispatch, maps Agent events into RunEvent, and commits suspension or terminal state. A failed active operation is durably settled before the Run terminal event, including deferred Program-child failure after resolver finalizers. `RuntimeWorker.layer` from `generalist/runtime/sql-driver` claims ready PostgreSQL Runs and executes them through this host.
- When a retryable model stream failure escapes after a completed turn, `RunExecutor` starts at most two more execution attempts in the same Run. Each attempt receives the canonical Session projection, continuation, and DriverCheckpoint; completed child and tool operations stay journaled and are not dispatched again. Attempts keep the Run ID, append `RunAttemptStarted`, preserve the worker fence, and terminalize with the original typed Runtime failure after attempt 3.
- `RunExecutor` dispatches tagged Agent and Program resolutions only after resolver attestation matches the persisted executable closure. Program tool calls and logs use stable named operation keys in `run_operations`; matching completed calls replay, changed inputs diverge, and unknown non-idempotent calls remain blocked for explicit resolution. Durable Program Agent runs, maps, and fan-outs atomically reserve the Program operation and budget with immutable child admission. Child terminal reconciliation closes the Program wait and makes the parent claimable without an application resume call.
- Opaque canonical JSON text is stored with schema codecs; correctness queries do not inspect JSON payloads.
- `layer(options)` from `generalist/mysql` is the durable multi-worker MySQL 8+ store. It has the same relational state machine, verify-only startup, database-time leases, monotonic Run and Session fences, stale-owner rejection, bounded fan-out claims, and Session-lane-head claims as PostgreSQL. `RuntimeSchema.plan`, `check`, `apply`, and `markDirty` from that package own predeploy schema work; `apply` serializes creation of the version 4 baseline with a named migration lock.
- MySQL transactions run at `READ COMMITTED`. Claims use bounded candidate scans plus primary-key `FOR UPDATE SKIP LOCKED`, and deadlocks retry the whole transaction. Conditional wait closes use same-connection `ROW_COUNT()`; other writes do not rely on `RETURNING`. Rows are read after fenced updates, booleans decode from `TINYINT(1)`, and timestamp strings decode at the store boundary. PostgreSQL proves the same transition with `UPDATE ... RETURNING`; SQLite and Cloudflare Durable Object SQLite use their returned-row mechanism.
- MySQL event delivery is polling-backed for local and cross-process followers. Each subscription owns its poller scope, registers before polling begins, and advances from committed durable history after the exclusive cursor.
